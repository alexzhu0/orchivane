## 2. 为什么有「首轮试跑」与「从冻结起点重跑」两段记录？

1. **首轮试跑（T1–T5）暴露的真实违规**：
   - 首轮 T1（建制）顺利通过；但在 T2 材料冻结之后，团队在 T3 过程中发现原冻结版《需求》里 05 号封面底图宽度前后写法冲突（表格写 `900` vs 正文写 `960`），以及原冻结版《验收标准》要求外部开发方在交付目录内自交两张浏览器截图（而外部工具在无浏览器/沙盒限制下无法自截）。
   - 首轮团队没有守住「冻结材料零改动」红线，而是开出两张变更单（`CHG-002`、`CHG-003`）直接修改了已冻结的《验收标准》和《需求》，且在更新两份早期记录时直接覆盖了原文件而未先留备份。
   - 因此，按测试方案红线，**首轮 T2 被如实判定为「不通过」**，并在首轮 T5 健康巡检（`HEALTH-001`）中登记为 `P-01`（严重）、`P-02`（中度）、`P-03`（轻度）三项问题单。
2. **经用户授权从冻结起点重跑（T2R–T5R）**：
   - 用户审阅首轮报告后，明确拍板**「守住原方案、从冻结那边重跑」**：测试母方案一字不改，T1 沿用首轮通过结论，从 T2 第 ③ 步冻结起点建立独立的重跑目录，把原冻结版 23 个文件原封不动锁入只读冻结区，重跑全程 **0 次修改冻结材料、0 张修改冻结材料的变更单**。
   - 对原冻结版内部的两处客观问题：05 号底图宽度冲突不改《需求》原文，按底图说明与表格统一按 `900` 判分并记入日志；开发方无法自截 png 不改《验收标准》原文，照原标尺如实判两版 `G3` 为「不通过（✗）」（非红线条目）。

## 6. 补充验证（2026-10-24）

> 本节是 2026-10-24 单独补做的小测试，不改上面 2026-10-23 的历史记录。这里的「通过」同样只按本测试事先定的标准判定，不代表上游已做 Grok Bot 兼容认证。审核 Bot 跑后核查：通过。

### 6.1 目的

按维护者第二条意见第 3 点，用一个只用 Grok Bot 的小场景检查三件事：执行 Bot 能否按固定版本手动读取 Orchivane 并回执就位；「派工 → 产物 → 回执 → 总控核验」的闭环换一份输入后能否再走通一次；遇到缺输入时能否停下、不编结果，补齐后用同一个任务编号恢复。

### 6.2 配置

| 项目 | 记录 |
|---|---|
| Orchivane | 0.4.1，`alexzhu0/orchivane` commit `f1b45702`；执行 Bot 读的是原文只读副本里的 `SKILL.md`、`references/setup.md`、`references/dispatch.md`（手动读取，没有安装插件） |
| 角色 | 一个总控 Bot（唯一派工方）+ 一个执行 Bot，都是团队里已有的 Grok Bot 队友，没有新建机器人 |
| 派工方式 | Grok Bot 自带的给队友发消息工具；派工消息发前存档，执行 Bot 的回消息照原文存档 |
| 写入范围 | 测试根目录 `<TEST_ROOT>`；执行 Bot 只许写 `03_产出/` 和 `04_回执/`，写到别处即算失败 |
| 输入 | 三份虚构 CSV（见下）；正确答案由总控事先算好封存，不给执行 Bot 看 |
| 证据 | 每步前后对 `<TEST_ROOT>` 拍 md5 快照（拍快照的命令原文已存档）；按时间标记列出新增文件；逐步核验记录、结果表、消息计数 |
| 不涉及 | 本地电脑、外部开发工具、业务资料、定时任务、付费服务；花费为 0 |
| Grok Bot 版本 | 未提供版本号 |

虚构输入（每份两列：任务名、预计分钟）：

- `T-01_清单.csv`：整理书架 20 / 浇花 10 / 写购物清单 15
- `T-02_清单.csv`：洗碗 15 / 叠衣服 25 / 倒垃圾 5
- `T-03_清单.csv`：擦桌子 10 / 喂猫 5 / 收快递 20（开始时故意不放）

每个任务都是：数数据行数、算总分钟、找分钟最长的一项，写进 `统计.md`。

### 6.3 步骤与结果

| 步 | 内容 | 结果 |
|---|---|---|
| 0 | 准备：放好 T-01、T-02 两份输入，封存答案，拍初始快照，确认 T-03 不存在 | 通过 |
| 1 | 加载与就位（`ORV-L0`）：执行 Bot 在自己的对话里读上述三个原文文件、自己算 md5，回执写版本、来源 commit、文件 md5、职责、可写目录和停止条件 | 通过：版本 0.4.1、commit `f1b45702`；三个 md5 `a445042a` / `3ec6967c` / `2b9342df` 与存档副本一致；职责和停止边界写全 |
| 2 | 正常闭环（`ORV-T01`，输入 T-01） | 通过：3 行 / 45 分钟 / 最长「整理书架」20，与封存答案一致；回执写了编号、输入和产物 md5；总控核验后才记「完成」 |
| 3 | 换输入重复（`ORV-T02`，输入 T-02） | 通过：3 行 / 45 分钟 / 最长「叠衣服」25，对上 T-02 的答案（不是 T-01 的）；T-01 的产物和回执 md5 未变 |
| 4 | 可控异常：缺输入（`ORV-T03`）。派工指向还不存在的 T-03，消息里不提示文件缺失 | 通过：执行 Bot 停下，只写了一份「受阻（缺输入）」回执；没有建产物、没有编数字、没有报完成；T-01、T-02 的文件未变；总控把任务记为「待处理」 |
| 5 | 恢复（`ORV-T03` 同一编号）：总控放好 T-03 输入，再发一条恢复消息 | 通过：只生成一份产物，3 行 / 35 分钟 / 最长「收快递」20，对上答案；回执先是受阻段，后面追加「恢复后完成」段，总控逐字节核对，前段的 md5 与原受阻回执一致；核验后才记「完成」 |

按快照 diff，在所监测目录 `<TEST_ROOT>` 内，第 1–5 步执行 Bot 新增或改动的文件都只在 `03_产出/` 和 `04_回执/` 里。所监测目录以外的情况见 6.5 第 1 条。

### 6.4 消息数

总控 Bot → 执行 Bot 共 5 条（第 1–5 步各 1 条），催问 0 条；事先定的上限是 8 条（含催问）。执行 Bot 每步回 1 条消息，原文存档。请审核 Bot 做跑后核查的消息不在被测的派工往来之内，不计入。

### 6.5 与事先方案的偏差和照实说明

1. **所监测目录以外的一次临时写入：** 第 5 步，执行 Bot 为了校验「受阻段没被改」，把回执复制到测试目录外的系统临时目录做比对，用完即删。快照只覆盖 `<TEST_ROOT>`，看不到这一步，所以回执里「只写了 `03_产出/ORV-T03/` 和本回执追加段」的说法不完全准确。按方案字面，这算写到了允许范围以外；审核 Bot 按目的（只为校验、没碰测试和业务目录、已删除）判为不记失败。本节关于写入范围的结论因此只说「所监测目录内」。
2. **快照多拍一张：** 方案只排了 S0–S5 六张快照，实际在第 1 步（加载）之后多拍了一张，第 2 步的 diff 是对这张比的（对 S0 的 diff 也另外列出）。
3. **T-03 的放入方式：** T-03 输入是用保留修改时间的复制（`cp -p`）放进去的，所以按时间标记用 `find -newer` 列不出它；放入记录（文件名和 md5）另外存档。新增文件以快照 diff 为准，不以 `find -newer` 为准。
4. **S5 之后还有一次改动：** S5 是第 5 步结束时的状态，不是测试目录的最终状态。之后总控的消息计数文件又改过一次，追加了发给审核 Bot 的那条消息的记录。
5. **受阻回执的措辞：** 执行 Bot 的回执原文写的是「受阻（缺输入）」，与方案措辞「未完成 / 待处理：输入缺失」不同、意思一致。「待处理」是总控在自己的记录里给任务标的状态，不是回执里的原话。

### 6.6 限制

- 只有一个总控 Bot 和一个执行 Bot；没有测多个执行 Bot。
- 只测了「缺输入」这一种异常；「没收到回执」没有测。
- 单次运行，每步各 1 次。第 3 步是换输入的新任务，不是把同一任务重复派一次；第 5.3 节里的「重复派工」「运行中断恢复」仍然未验证。
- 写入范围只按所监测目录核查；目录外的写入快照看不到（见 6.5 第 1 条）。
- 贡献者报告，维护者未独立复核。

### 6.7 另一条观察

测试期间，执行 Bot 除了回复总控，还直接向用户发过进度消息。派工里没有禁止这一点，也不影响上面的结果；以后派工应写明执行角色只回总控。

结论：在该配置和这些场景下可重复。这不表示对 Grok Bot 的支持已经稳定，也不是兼容认证。
