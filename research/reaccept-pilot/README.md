# Orchivane 变更后重新验收试跑
使用 Python 3.9 或更新版本运行 python3 check.py。observed.txt 是本次正常输出。check.py 是本案例的只读原型，退出 0 表示指定快照核验通过，业务判定见下文。

输入取自 Orchivane 仓库 examples/tool-library，从本地 Git 版本 fb32e7906479785274bdde7ca04c2a87c204c7bb 复制冻结资料。此为真实项目记录的离线回放，借物业务本身是虚构演练。case/D2-Q2.md 是 B 的变更要求，case/acceptance.md 为 A 的既有证据。新验收会话仅获准读取 case 中的交接资料，不含历史 B 结论。

## 结果
- B 清单中四份文件摘要均一致。研究文件及研究回执内容沿用 A；研究证据仅适用于原核验时点。
- A 冻结方案内两条相对引用均无法定位，B 两条均在包内可读。
- 库存 CSV 的 20 处变化均在 notes 列。方案文本变化须做语义复核。
- 在副本中同时改动 CSV 和移除研究回执，检查器报告两项错误，退出 1。自行复跑可复制 case，在复制目录操作，再运行 python3 check.py COPY_DIRECTORY。
- 新会话独立找到 B 方案第25、37行冲突。一个已停用、无未还流水的物品遇到账实不符，第25行令其立即进入待检，第37行要求先复核。交付仍暂停，问题在状态转换条件。结论为不通过，与历史 Q2 的关键发现一致。新会话另提出已取消或过期的待取物品被核为损坏时第28行通往第17行的分支，值得澄清“复核未通过”的优先级，未计作第二个已证实缺陷。
- 没有两组真人计时，不能据此计算节约分钟数。独立接班使用临时新模型会话，没有验证产品原生聊天的创建、归档或崩溃恢复。

原始案例和历史判定：https://github.com/alexzhu0/orchivane/tree/d6bc2220f17c290cc4f0a5fe43a804eb2e48a625/examples/tool-library

## 独立评分与历史评分的差异
新会话给出 18/20，标记 I4、X7 未通过，两项均源于同一反例。历史 Q2 为 19/20，只判 I4 未过，认为 X7 所要求的未知 ID 和账实不符处理已有可执行路径。本轮保留两种归项；二者对规则冲突与整体不通过的判断一致。先冻结跨检查项的归分标准，再做对照计时。
